# 需求分析与范围

## 1. 问题不是“企业缺一个聊天框”

假设某工业网关企业维护多份手册和接口说明。售前人员收到客户问题后，要确认型号、固件版本和适用条件，再向研发确认。困难可能来自资料分散，也可能来自资料本身过期、参数冲突或责任人不清。

这是待验证的场景假设，没有实际客户调研记录。不能把“模型能回答”直接等同于“售前效率提升”。

## 2. 用户与任务

| 角色 | 当前任务 | 主要风险 | 需要的证据 |
| --- | --- | --- | --- |
| 售前工程师 | 准备答复和演示材料 | 引用错型号或过期参数 | 型号、版本、原文、适用边界 |
| 产品/资料维护人 | 发布与更新手册 | 旧版仍被检索 | 导入状态、有效版本、撤销记录 |
| 技术审核人 | 处理难题和冲突 | 重复追问信息、责任不清 | 问题上下文、已查资料、待确认点 |
| 管理员 | 配置身份与访问范围 | 内部文件外泄 | 权限策略、审计与撤销能力 |

客户是信息最终使用者，但不是首期系统直接用户。该区别决定首期要保留人的审核与发送环节。

## 3. 假设登记与访谈提纲

| 假设 | 如何验证 | 若不成立怎么调整 |
| --- | --- | --- |
| 查找资料是高频耗时环节 | 观察一次完整答复过程，记录找资料与等待确认耗时 | 若主要卡在审批，应先改流程 |
| 文档版本可明确标记 | 抽查目录及发布制度 | 先做资料治理，不急着接模型 |
| 常见问题能从现有资料回答 | 由工程师标注历史问题与来源 | 无答案比例高则优先补充FAQ |
| 售前愿意核对引用 | 让用户执行查找与复核任务 | 优化原文定位，不只优化聊天 |
| 企业允许指定环境处理文档 | 与安全负责人确认数据边界 | 无外发许可则评估本地部署 |

拟访谈5-8名售前、2名技术审核人和1名资料维护人；数量为计划，尚未执行。询问最近一次实际问题，不问“你会不会喜欢AI”。

访谈重点：问题来源与频率、错误答复的代价、资料权限、版本确定方式、哪些场景必须人工确认、客户回复流程。只有取得授权的脱敏记录才可用于评测，不能上传客户原件到公开仓库。

## 4. 用户任务拆解

收到问题 → 确认型号与版本 → 搜索资料 → 核对参数和出处 → 起草答复 → 必要时技术审核 → 人工发送 → 记录未解决问题。

方案对应：问题补充字段 → 版本过滤 → 可读资料检索 → 引用原文 → 草稿 → 工单 → 反馈回流。首期不改变人工发送责任。

## 5. 优先级

| 需求 | 优先级 | 理由 | 验证成本 |
| --- | --- | --- | --- |
| 有出处的型号/版本问答 | P0 | 避免错误参数被当作承诺 | 人工标注资料和问题 |
| 缺信息补问、无依据拒答 | P0 | 比流畅但错误的回答更重要 | 设计不可答测试集 |
| 身份、文档范围与引用鉴权 | P0 | 不应以体验为由牺牲保密性 | 后端负向安全测试 |
| 文档状态、发布与失效版本 | P0 | 先保证来源可信 | 文档管理流程测试 |
| 反馈、人工接管与审核记录 | P0 | 形成可追踪的纠错入口 | 小范围人工验证 |
| 答复导出与模板化 | P1 | 减少复制整理工作 | 对比人工编辑耗时 |
| 多语言生成与CRM集成 | P2 | 首期缺少需求证据 | 另行验证与接口审批 |

P0来自风险与前置依赖判断，不是使用虚构数据算出的RICE分。

## 6. 为什么选RAG而不是先微调

设计假设：资料会更新，答复需要原文和版本。RAG更便于更换来源并溯源；微调不能保证记住最新参数或正确执行访问权限。若资料少、任务固定，带来源的关键词搜索也可能够用，因此试点必须与搜索基线比较，而非只和“没有工具”比较。

长上下文可用于少量明确文件的集中审阅，不直接解决资料权限、版本治理和大量文档定位。Agent涉及动作与额外权限，本期没有必要为纯问答引入自主执行。
